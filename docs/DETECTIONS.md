### Cron Persistence Written Outside Package Management

`detections/linux/cron_persistence.yml` &middot; **medium** &middot; ATT&CK T1053.003

Detects a cron entry being created that invokes a network client or an interpreter. Package managers install cron jobs too, so the payload rather than the write is what makes this interesting.

**Telemetry source.** Sysmon for Linux Event ID 1, or auditd execve

**Elastic query (kuery).**

```
((process.command_line : "*crontab -*" or process.command_line : "*/etc/cron.d/*" or process.command_line : "*/var/spool/cron/*") and (process.command_line : "*curl*" or process.command_line : "*wget*" or process.command_line : "*/dev/tcp/*" or process.command_line : "*base64*" or process.command_line : "*python*" or process.command_line : "*perl*" or process.command_line : "*bash -i*") and not (process.parent.name : "dpkg" or process.parent.name : "apt" or process.parent.name : "rpm" or process.parent.name : "yum" or process.parent.name : "dnf"))
```

**Investigation fields.** process.command_line, process.parent.name, user.name

**Investigation path.**

1. Read the full cron entry and resolve what it executes.
2. Check the file modification time of the crontab against the process timestamp.
3. Determine whether a configuration management agent was the parent.
4. Look for the same entry on comparable hosts.

**Known false positives.**

- Configuration management such as Ansible or Puppet writing cron entries. Filter on the parent process of the automation agent.

**Validation.** 1 true-positive fixture(s) in `telemetry/true_positive/cron_persistence.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### Remote Script Downloaded and Piped Directly to a Shell

`detections/linux/curl_piped_to_shell.yml` &middot; **high** &middot; ATT&CK T1059.004, T1105

Detects curl or wget output piped straight into a shell. Nothing is written to disk for a scanner to inspect, and the fetched content is executed with the caller's privileges, so this is a common first-stage installer for Linux implants and cryptominers.

**Telemetry source.** Sysmon for Linux Event ID 1, or auditd execve

**Elastic query (lucene).**

```
((process.command_line:*curl* OR process.command_line:*wget*) AND process.command_line:/.*\|\s*(sudo\s+)?(ba|z|k|da)?sh\b.*/)
```

**Investigation fields.** process.command_line, process.parent.name, user.name, host.name

**Investigation path.**

1. Retrieve the script from the URL in a sandbox rather than on the affected host.
2. Check whether the host is a build agent, where this pattern is routine.
3. {'Look for what the script installed': 'new services, cron entries, or listening sockets.'}
4. Check outbound connections from the host after the event.

**Known false positives.**

- Documented installation instructions for developer tooling use this pattern. On a server outside a build pipeline it should be rare enough to alert on.

**Validation.** 2 true-positive fixture(s) in `telemetry/true_positive/curl_piped_to_shell.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### Failed Windows Logon

`detections/auth/failed_logon_burst.yml` &middot; **informational** &middot; ATT&CK T1110

Base rule matching a single failed interactive or network logon. It is not intended to alert on its own; the correlation rule below applies the threshold.

**Telemetry source.** Windows Security channel

**Elastic query (kuery).**

```
event.code : "4625"
```

**Investigation fields.** user.name, source.ip, host.name

**Investigation path.**

1. Determine whether all failures share one source address and one logon type.
2. Check whether the account eventually authenticated successfully, which converts this into a compromise investigation.
3. For a single source and single account, a stale cached credential is the most common benign cause.
4. For many accounts from one source, treat as spraying and check which accounts succeeded.

**Known false positives.**

- Expired passwords and stale saved credentials on service accounts.

### Signed Binary Proxy Execution via rundll32 or regsvr32

`detections/windows/lolbin_proxy_execution.yml` &middot; **high** &middot; ATT&CK T1218.010, T1218.011

Detects rundll32 or regsvr32 executing content from a remote location or from a user-writable path. Both are Microsoft-signed and allowed by most application control policies, which is exactly why they are used to run attacker code.

**Telemetry source.** Sysmon Event ID 1 (process creation), or Security 4688

**Elastic query (kuery).**

```
((process.name : "rundll32.exe" or process.name : "regsvr32.exe") and ((process.command_line : "*http://*" or process.command_line : "*https://*" or process.command_line : "*\\\\\\\\*" or process.command_line : "*scrobj.dll*" or process.command_line : "*{'javascript': None}*" or process.command_line : "*{'vbscript': None}*") or (process.command_line : "*\\AppData\\Local\\Temp\\*" or process.command_line : "*\\Users\\Public\\*" or process.command_line : "*\\Downloads\\*")))
```

**Investigation fields.** process.command_line, process.parent.name, user.name

**Investigation path.**

1. Extract the URL or file path being loaded and inspect the content.
2. Check the parent process, since a browser or Office parent changes the assessment.
3. Look for application control logs that would have recorded the same execution.
4. Confirm whether the loaded DLL or scriptlet is a known enterprise component.

**Known false positives.**

- Some enterprise software registers COM objects from ProgramData during install. Scope by parent process where that occurs.

**Validation.** 2 true-positive fixture(s) in `telemetry/true_positive/lolbin_proxy_execution.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### Credential Dumping Indicators Against LSASS

`detections/windows/lsass_credential_access.yml` &middot; **critical** &middot; ATT&CK T1003.001

Detects processes reading LSASS memory or command lines that name LSASS alongside a dumping utility. LSASS holds cached credential material, so a memory dump of it is a direct precursor to lateral movement.

**Telemetry source.** Sysmon Event ID 10 (process access)

**Elastic query (kuery).**

```
((((winlog.event_id : "10" and process.target.name : "*\\lsass.exe") and (process.access_mask : "*0x1010*" or process.access_mask : "*0x1410*" or process.access_mask : "*0x143a*")) or (process.command_line : "*lsass*" and (process.command_line : "*procdump*" or process.command_line : "*comsvcs.dll*" or process.command_line : "*MiniDump*" or process.command_line : "*rundll32*"))) and not (process.executable : "C:\\Program Files\\Windows Defender\\*" or process.executable : "C:\\Windows\\System32\\wbem\\*"))
```

**Investigation fields.** process.name, process.executable, process.command_line, process.target.name, user.name

**Investigation path.**

1. {'Treat as an incident until disproved': 'assume credentials on the host are exposed.'}
2. Identify the accessing process and whether it is a known security product.
3. Look for a dump file written near the event, and for its later exfiltration.
4. Force a password reset for accounts with sessions on that host, including service accounts.

**Known false positives.**

- Endpoint protection products and crash-reporting agents legitimately open LSASS. Baseline the accessing image path before enabling this rule in production.

**Validation.** 2 true-positive fixture(s) in `telemetry/true_positive/lsass_credential_access.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### PowerShell Download Cradle

`detections/windows/powershell_download_cradle.yml` &middot; **high** &middot; ATT&CK T1059.001, T1105

Detects a PowerShell command line that both retrieves remote content and executes it in memory. The pairing matters: a download alone is ordinary, and Invoke-Expression alone is ordinary, but together they are the standard shape of a staged payload that never touches disk.

**Telemetry source.** Sysmon Event ID 1 (process creation), or Security 4688

**Elastic query (kuery).**

```
((process.name : "powershell.exe" or process.name : "pwsh.exe") and (process.command_line : "*DownloadString*" or process.command_line : "*DownloadFile*" or process.command_line : "*DownloadData*" or process.command_line : "*Invoke-WebRequest*" or process.command_line : "*Net.WebClient*" or process.command_line : "*iwr*" or process.command_line : "*curl*") and (process.command_line : "*IEX*" or process.command_line : "*Invoke-Expression*" or process.command_line : "*| iex*" or process.command_line : "*Start-Process*"))
```

**Investigation fields.** process.command_line, process.parent.name, user.name

**Investigation path.**

1. Extract the URL and check its reputation and first-seen date. Newly registered domains are a strong signal.
2. Look for the fetched content on disk or in the PowerShell operational log (Event ID 4104 records script blocks).
3. Check outbound connections from the host around the event timestamp for the same destination.
4. If the URL is an internal artefact repository, this is likely a deployment script; confirm with the owning team.

**Known false positives.**

- Package bootstrap scripts such as the Chocolatey installer follow exactly this pattern. Allow-list by the specific URL host rather than by the technique.

**Validation.** 2 true-positive fixture(s) in `telemetry/true_positive/powershell_download_cradle.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### PowerShell Encoded Command Execution

`detections/windows/powershell_encoded_command.yml` &middot; **high** &middot; ATT&CK T1027, T1059.001

Detects powershell.exe invoked with an encoded command payload. Encoding is used to keep the real command out of the command line that defenders and logging see, and is common in loaders delivered by phishing documents.

**Telemetry source.** Sysmon Event ID 1 (process creation), or Security 4688

**Elastic query (kuery).**

```
((process.name : "powershell.exe" or process.name : "pwsh.exe" or process.executable : "*\\powershell.exe") and (process.command_line : "* -enc *" or process.command_line : "* -encodedcommand*" or process.command_line : "* -e *" or process.command_line : "* -ec *"))
```

**Investigation fields.** process.command_line, process.parent.name, user.name, host.name

**Investigation path.**

1. {'Decode the payload': 'the argument after -enc is Base64 of UTF-16LE text. `base64 -d | iconv -f UTF-16LE` returns the real command.'}
2. Identify the parent process. An Office application or a browser as parent moves this straight to incident handling.
3. Check whether the decoded command reaches the network, and pivot on that host or URL across the estate.
4. Confirm whether the account normally runs PowerShell at all.

**Known false positives.**

- Configuration management and deployment tooling that wraps PowerShell payloads, notably SCCM and some backup agents. Baseline the parent process before alerting.

**Validation.** 3 true-positive fixture(s) in `telemetry/true_positive/powershell_encoded_command.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### Autorun Registry Key Written With a Suspicious Payload

`detections/windows/registry_run_key_persistence.yml` &middot; **medium** &middot; ATT&CK T1547.001

Detects a value being written to a Run key where the payload points at a script interpreter or a binary in a user-writable directory. Writing to Run keys is normal for installed software; the combination with a scripting host or a temp path is not.

**Telemetry source.** Sysmon Event ID 12/13 (registry value set)

**Elastic query (kuery).**

```
((registry.path : "*\\CurrentVersion\\Run\\*" or registry.path : "*\\CurrentVersion\\RunOnce\\*" or registry.path : "*\\CurrentVersion\\Explorer\\Shell Folders\\Startup*") and (registry.data.strings : "*powershell*" or registry.data.strings : "*wscript*" or registry.data.strings : "*cscript*" or registry.data.strings : "*mshta*" or registry.data.strings : "*rundll32*" or registry.data.strings : "*\\AppData\\Local\\Temp\\*" or registry.data.strings : "*\\Users\\Public\\*" or registry.data.strings : "*\\ProgramData\\*"))
```

**Investigation fields.** registry.path, registry.data.strings, process.name, user.name

**Investigation path.**

1. Resolve the target binary and check its signature and creation time.
2. Determine which process wrote the value and what started that process.
3. Check whether the same value name appears on other hosts.
4. Legitimate installers write Run keys; the writing process being a script host is the discriminator.

**Known false positives.**

- Installers that place updater shims under ProgramData. Confirm the publisher of the target binary before escalating.

**Validation.** 1 true-positive fixture(s) in `telemetry/true_positive/registry_run_key_persistence.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### Scheduled Task Created From a Command Shell

`detections/windows/scheduled_task_persistence.yml` &middot; **medium** &middot; ATT&CK T1053.005

Detects schtasks.exe creating a task. Scheduled tasks are a common persistence mechanism because they survive reboot and run without an interactive session. The signal is weak on its own, so the rule records the parent process to support triage rather than to justify an alert by itself.

**Telemetry source.** Sysmon Event ID 1 (process creation), or Security 4688

**Elastic query (kuery).**

```
((process.name : "schtasks.exe" and process.command_line : "*/create*") and not user.name : "*$")
```

**Investigation fields.** process.command_line, process.parent.name, user.name

**Investigation path.**

1. Read the task action. The action, not the task creation, determines whether this matters.
2. Check the task author and whether the binary it runs is signed.
3. Look for a matching task on other hosts.
4. Compare against the software deployment schedule before escalating.

**Known false positives.**

- Software installers routinely register update tasks. Expect a high base rate and triage on the task action rather than on the creation event alone.

**Validation.** 1 true-positive fixture(s) in `telemetry/true_positive/scheduled_task_persistence.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### Service Creation Consistent With Remote Execution Tooling

`detections/windows/service_creation_remote_exec.yml` &middot; **high** &middot; ATT&CK T1021.002, T1569.002

Detects Windows service installation events whose service name or image path matches remote execution utilities. PsExec and its reimplementations work by writing a service binary to ADMIN$ and registering it, so the service installation event is the durable artefact.

**Telemetry source.** Windows System channel

**Elastic query (kuery).**

```
(event.code : "7045" and ((service.name : "*PSEXESVC*" or service.name : "*PAExec*" or service.name : "*RemComSvc*" or service.name : "*CSExec*") or (file.path : "*\\PSEXESVC.exe*" or file.path : "*\\paexec*" or file.path : "*\\RemComSvc.exe*")))
```

**Investigation fields.** service.name, file.path, user.name, host.name

**Investigation path.**

1. Identify the account that installed the service and the source host it authenticated from (Security 4624, logon type 3).
2. Check whether the same service name appears on other hosts in the same window, which indicates lateral movement.
3. Confirm whether an administrator was performing sanctioned remote work at that time.
4. Preserve the service binary before it is deleted; PsExec removes it on disconnect.

**Known false positives.**

- Administrators who use PsExec as a sanctioned remote administration tool. Where that is the case, scope the rule to source hosts outside the administrative subnet.

**Validation.** 2 true-positive fixture(s) in `telemetry/true_positive/service_creation_remote_exec.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### Sudo Invocation of a Shell or Interpreter

`detections/auth/sudo_privilege_escalation.yml` &middot; **medium** &middot; ATT&CK T1548.003

Detects sudo being used to launch an interactive shell or a language interpreter. Both give an unrestricted root session, which defeats the point of granting narrow sudo rules, and is the usual outcome of exploiting a permissive sudoers entry.

**Telemetry source.** Sysmon for Linux Event ID 1, or auditd execve

**Elastic query (lucene).**

```
((process.name:"sudo" AND process.command_line:/.*\bsudo\s+(-\w+\s+)*(\/bin\/|\/usr\/bin\/)?(ba|z|k|da)?sh\b|\bsudo\s+(-\w+\s+)*(python[0-9.]*|perl|ruby|lua)\b.*/) AND NOT user.name:"root")
```

**Investigation fields.** process.command_line, user.name, host.name

**Investigation path.**

1. Check the sudoers entry that permitted this, since a narrow rule being used to spawn a shell suggests a misconfiguration.
2. Review the commands executed in the resulting root session.
3. Confirm whether the account is expected to hold administrative rights.
4. Where sudo is scoped intentionally, treat repeated occurrences as a policy gap rather than an attack.

**Known false positives.**

- Administrators who legitimately hold full sudo rights. The rule is most useful where sudo is scoped to specific commands.

**Validation.** 2 true-positive fixture(s) in `telemetry/true_positive/sudo_privilege_escalation.jsonl` must match; all 21 events in the benign baseline must not. Enforced by `tests/test_detections.py`.

### Failed Logon Burst Against a Single Account

`detections/auth/failed_logon_burst.yml` &middot; **high** &middot; correlation (event_count)

Ten or more failed logons for one account within five minutes. This is the shape of password guessing against a known user, as distinct from spraying, which is covered separately because it is wide rather than deep and would stay under this threshold.

**Aggregation.** event_count gte 10 within 5m, grouped by user.name

**Known false positives.**

- A user with a cached credential on a phone or mapped drive after a password change. Check whether all failures share one source address and one logon type.

**Validation.** Fires on `telemetry/true_positive/authentication_bursts.jsonl` and stays silent on the benign baseline, including the isolated failed logons it contains. Sub-threshold and time-spread variants are asserted not to fire.

### Password Spraying Across Multiple Accounts

`detections/auth/failed_logon_burst.yml` &middot; **high** &middot; correlation (value_count)

A single source address failing to authenticate against ten or more distinct accounts within fifteen minutes. Spraying stays below per-account lockout thresholds by trying one or two passwords against many users, so the distinguishing feature is breadth from one origin.

**Aggregation.** value_count gte 10 within 15m, grouped by source.ip, counting distinct user.name

**Known false positives.**

- A misconfigured application server or NAT gateway presenting many users from one address. Confirm whether the source is a shared egress point before treating it as an attacker.

**Validation.** Fires on `telemetry/true_positive/authentication_bursts.jsonl` and stays silent on the benign baseline, including the isolated failed logons it contains. Sub-threshold and time-spread variants are asserted not to fire.
